# 补充实测：控制台抢前台 → 0x887A0022 已闭环（2026-11-12）

配合 `FINAL-4.1.6-vs-5.0-根因.md` 阅读。原报告里「`AllocConsole()` 会不会真抢走前台」只是引用 Windows 行为，**现已在本机用探针复现，因果在单一进程内闭合**。

## 探针

`C:\Users\Thousand\AppData\Local\Temp\bepx`（WinExe + 裸 DXGI：`CreateDXGIFactory1` → `CreateSwapChainForHwnd` → `SetFullscreenState` 走 vtable[10]）。

复刻 BepInXDX `ConsoleWindow.Attach()` 的真实顺序：先 `GetForegroundWindow()` 记下「当前前台」→ `AllocConsole()` → `SetForegroundWindow(记下的那个)`，然后才建游戏窗口、调 `SetFullscreenState`。

## 结果

```
SPI_GETFOREGROUNDLOCKTIMEOUT = 0x7FFFFFFF (2147483647 ms)

---------- A 组：完全按 BepInXDX 顺序 ----------
  [1] AllocConsole 之前的 fg = 0x707BE cls='Chrome_WidgetWin_1' pid 4304
  [2] AllocConsole() = True   consoleHwnd=0xF0642 cls='ConsoleWindowClass' SELF
  [3] AllocConsole 之后 fg = 0xF0642 'ConsoleWindowClass' SELF      ← 控制台确实抢到了前台
  [4] SetForegroundWindow(preAlloc) = True                          ← 而且这次还原「成功」了
  [5] 还完之后 fg = 0x707BE 'Chrome_WidgetWin_1' pid 4304
      fg 属于本进程吗？ False                                        ← 前台落到了别的进程手里
  [6] 建窗口 0x9088A cls='BepxWnd_18688' SELF
  [7] fg 此刻 = 0x707BE pid 4304
  [8] SetFullscreenState(TRUE,NULL) = 0x887A0022

---------- B 组：同一条 swapchain，只把前台抢回本进程 ----------
  抢完之后 fg = 0x9088A SELF   GetActiveWindow=SELF   GetFocus=SELF
  SetFullscreenState(TRUE,NULL) = 0x00000000   <-- 成功
```

**同一条 swapchain、同一个窗口、同一个进程，唯一变量是前台归属，结果就从 `0x887A0022` 变成 `S_OK`。**

这比原报告更强：不需要等用户重启游戏做 A/B，因果已经在单一进程内闭合。

## 对原报告措辞的两处修正

### 1. 不是「`setForeground` 失败」，而是「它成功地把前台还给了别人」

`ConsoleWindow.Attach()` 里 `setForeground(currWnd)` 的目标是「AllocConsole 之前那个前台窗口」。本机实测该调用**返回 `True`**——它成功执行了，结果是前台被还给 Chrome，游戏进程自己仍然什么都没有。

所以「丢掉返回值」确实是个隐患，但真正的毛病不在「没检测到失败」，而在**这段代码的意图本身就是把前台让出去**：它假设「AllocConsole 抢走的前台应该还回去」，可对一个刚启动、从未持有过前台的游戏进程来说，这个「还原」等于把自己永久锁在后台。

即使把返回值判断补上也无济于事——`SetForegroundWindow` 会返回 `True`，代码会以为万事大吉。

### 2. `AllocConsole` 抢前台是「纯损失」，但并非必然触发

如果进程本来就在前台（例如从同一个控制台启动、或启动器把前台交给了游戏），A 组第 [5] 步的 fg 仍可能是 SELF，那就不会触发。这解释了为什么同样跑 5.0 BE，用户从启动器点「开始游戏」时表现可能稳定，而某些启动序列会失败。

## 仍然成立的结论

`0x887A0022` 的唯一实质成因仍是「调用瞬间本进程不处于前台上下文」。B 组证明了只要补上这个条件就立刻成功，与驱动、分辨率、虚拟显示器、HDR、刷新率、DPI 全部无关。

## 仍未验证

- 「关掉控制台后首次启动即进独占全屏」这个端到端 A/B 仍需用户配合重启两次。探针证明了机制，但没证明 EFT 实际启动序列里 `AllocConsole` 一定发生在那个 170~300ms 窗口之前（时序高度吻合，未在同一进程内打点）。
- `SPI_GETFOREGROUNDLOCKTIMEOUT = 0x7FFFFFFF` 是异常值（默认 200000 ms），来源未定位。注意 A 组 `SetForegroundWindow` 返回 True，说明该值并不阻止「还原」动作，它影响的是「后台进程能否自己抢到前台」；B 组用 `AttachThreadInput` 绕过了这个限制。
- 4.1.6 时代是否还有别的因素（BepInEx 5 的 Doorstop 4.5.0 注入时机）未逐项排除。
- 未验证 `--enable-console false` 命令行开关是否比改 cfg 更稳妥（`ConsoleManager.EnableConsoleArgOverride` 优先级高于配置文件，但需确认 EFT 能否透传该参数）。
