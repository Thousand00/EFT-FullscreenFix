# 4.1.6 能进独占全屏、5.0 BE 不能——代码级根因

结论：**是 BepInEx 注入器换代带来的默认配置差异，不是游戏代码、不是 SPT 代码。**

## 一行结论

BepInXDX 6（5.0 用）的 `[Logging.Console] Enabled` 默认值是 **`true`**；
BepInXDX 5（4.1.6 用）是 **`false`**。
开启后会调 `AllocConsole()` 凭空创建一个控制台窗口，抢走前台，随后 `setForeground(currWnd)` 的返回值被丢弃、不检查是否成功。前台一旦丢失，本机（`SPI_GETFOREGROUNDLOCKTIMEOUT = 0x7FFFFFFF`，永远不会超时）就再也要不回来 —— 而 EFT 恰好在进程启动后 170～300ms 那个窗口里申请独占全屏，于是必被 DXGI 拒绝（`0x887A0022`）。

## 证据链（五条，全部可复核）

### 1. 两版控制台默认值不同（决定性）

| | 4.1.6 | 5.0 BE |
|---|---|---|
| BepInEx 世代 | BepInXDX **v5.4.23.5**（BepInEx 5） | BepInXDX **6.0.0-be.35**（BepInEx 6） |
| 定义位置 | `BepInEx/Console/ConsoleManager.cs` | `BepInEx.Core/Console/ConsoleManager.cs` |
| 绑定代码 | `ConfigFile.CoreConfig.Bind("Logging.Console", "Enabled", false, ...)` | `ConfigFile.CoreConfig.Bind("Logging.Console", "Enabled", true, ...)` |
| **出厂默认** | **`false`** | **`true`** |

本机实际部署（commit `08c2ac09c7f8fd7aef56a8b5ebd7a03e2f956442`）复核：默认值确为 `true`。
本机 `D:\EFT-5.0 BE\BepInEx\config\BepInEx.cfg` 第 101 行 `Enabled = true`，注释 `# Default value: true`，**是插件自己生成的出厂值，不是手工改的**。
SPT 官方 4.1.6 分发包 `SP-Tushonka/build@4.1.6` 的 `build-4.0-assets/BepInEx/config/BepInEx.cfg` 里，`Enabled = false` 且注释 `# Default value: false`。

### 2. `Enabled = true` 会真的创建一个窗口，并抢前台

`Runtimes/Unity/BepInEx.Unity.IL2CPP/Preloader.cs:37-41`：
```csharp
if (ConsoleManager.ConsoleEnabled)
{
    ConsoleManager.CreateConsole();
    Logger.Listeners.Add(new ConsoleLogListener());
}
```
`BepInEx.Core/Console/ConsoleManager.cs:116-129` `CreateConsole()` → `Driver.CreateConsole(codepage)`
`BepInEx.Core/Console/Windows/WindowsConsoleDriver.cs:88-89` `public void CreateConsole(uint codepage) => ConsoleWindow.Attach();`
`BepInEx.Core/Console/Windows/ConsoleWindow.cs:52-73`：
```csharp
var cur = GetConsoleWindow();
if (cur == IntPtr.Zero)
{
    var currWnd = getForeground();          // 记下当前前台
    if (!AllocConsole()) { ... }            // ★ 创建控制台窗口 —— 系统会把前台给它
    setForeground(currWnd);                 // ★ 返回值被丢弃，失败也继续
}
```
`setForeground` 是 `SetForegroundWindow` 的函数指针（`:127` `setForeground = GetProc<SetForegroundWindowDelegate>(user32Dll, "SetForegroundWindow");`），返回 `bool`，**调用处没有判断**。

> **2026-11-12 实测修正**：本机探针证明这次 `setForeground` 其实**返回 `True`**——它成功地把前台还给了「原来那个窗口」，也就是**另一个进程**。所以真正的毛病不是「没检测到失败」，而是这段代码的意图本身就把前台让了出去。详见 `FINAL-补充实测-控制台抢前台闭环.md`。

### 3. 本机前台一旦丢失就再也拿不回来

实测 `SystemParametersInfo(SPI_GETFOREGROUNDLOCKTIMEOUT) = 0x7FFFFFFF`（2147483647 ms）。
即 Windows 的前台锁定超时被设成了「永不超时」，任何后台进程都无法自动取得前台，`SetForegroundWindow` 会静默失败。

而 t4 的实测结论是：**进程曾持有前台又丢失 → 后续所有 `SetFullscreenState` 全部返回 `0x887A0022`，32 秒内不自愈；推回前台立刻恢复。**
`AllocConsole()` 抢走前台 + `setForeground` 失败 ⇒ 游戏进程在整个启动建窗期都处于「失去前台」状态。

### 4. 时间窗恰好撞上

t6 实测：EFT 申请独占全屏那一刻发生在 `Application awaken` 之后 **170～300ms**（6 次测量：+169/+170/+178/+278/+290/+303ms），整件事在进程启动后约 2.2s。
BepInEx 的 Preloader 是在 Unity 引擎初始化之前跑的（Doorstop 在 `EscapeFromTarkov.exe` 入口劫持），`CreateConsole()` 就在 Preloader 最开头 —— **早于、且紧邻** 那个 170～300ms 的窗口。

### 5. 事后为什么还能手动切成

用户按 F9 / 手动切显示模式时，是用户自己点回了游戏窗口 —— 前台回到游戏进程，前述锁定被打断，`SetFullscreenState` 随即成功。这也解释了 K 系列 v0.4.0 为什么有效：它等主菜单出现（用户已经和窗口交互过）之后才申请。

## 为什么 SPT 客户端侧的两处补丁都不是原因

| 项 | 4.1.6 | 5.0 | 是否差异 |
|---|---|---|---|
| `PlayerPrefs` 重定向 | Harmony Prefix 挂托管方法（10 个，全 `return false`） | `il2cpp_add_internal_call` 挂 10 个 icall | 形式上不同，但**两者都拦不住原生 `RegSetValueExA`**，且两版全仓对 `Screenmanager`/`Fullscreen mode` 均 0 命中 |
| PrePatch | Mono.Cecil 静态改 IL，`ChangeAppDataPath` 只改图标缓存目录 | 原生层改机器码，`SPTushonka.PrePatch/` 对 `appdata\|playerprefs\|registry\|settingsfolder` 0 命中、`Screen\|Display\|fullscreen` 0 命中 | 都不碰显示 |
| 启动器启动参数 | `-force-gfx-jobs native -token=... -config=...` | 逐字相同 | 否 |
| `boot.config` / exe manifest | — | 除 build-guid 外逐字节相同 | 否 |
| launcher 的 delta 补丁目标 | `Assembly-CSharp.dll.delta` | `global-metadata.dat.delta` | 是差异，但只是跟着 Mono→IL2CPP 变，`FilePatcher` 机制未变 |

## 这与 t6 的根因判定是什么关系

t6 判定的是「一次偶发失败如何被固化成永久失效」：DXGI 拒绝 → 引擎把实际落地的无边框**当场写回 HKCU** → 下次连申请都不做。那是**放大机制**。

本报告补的是**上游**：为什么 4.1.6 不会失败、5.0 会失败。答案是 BepInXDX 换代把控制台默认打开，凭空制造了一次抢前台。

两者串起来：
```
BepInXDX 6 默认开控制台
   → AllocConsole() 抢走前台，setForeground 失败（前台锁永不超时）
   → 170~300ms 后 EFT 申请独占全屏，进程不在前台 → 0x887A0022
   → Unity 回退 FullScreenWindow
   → 引擎把「实际落地模式=1」同步写回 HKCU Screenmanager Fullscreen mode_h3630240806
   → 下次启动读到 1，连申请都不做 → 永久无边框
```

## 可立即验证 / 可立即生效的两条

1. **验证**：把 `D:\EFT-5.0 BE\BepInEx\config\BepInEx.cfg` 里 `[Logging.Console]` 的 `Enabled` 改成 `false`，然后启动游戏。若首次启动即进独占全屏，则本判定成立。
2. **等价修法**：命令行加 `--enable-console` 是开启的开关，相反的关闭方式是配置改成 false（`ConsoleManager` 里 `ENABLE_CONSOLE_ARG = "--enable-console"` 只用于强制开启，没有强制关闭的参数）。

## 未验证项（诚实标注）

- 本判定依赖「`AllocConsole()` 确实会抢走前台」这一 Windows 行为。**已闭环**：见 `FINAL-补充实测-控制台抢前台闭环.md`，同一条 swapchain 只改前台归属即从 `0x887A0022` 变 `S_OK`。
- 但仍未做「开启控制台 vs 关闭控制台」的游戏级 A/B（需用户配合重启两次）。
- 本机 `SPI_GETFOREGROUNDLOCKTIMEOUT = 0x7FFFFFFF` 是一个异常值（正常默认 200000 ms），推测由某个常驻程序改的，未定位来源。注意实测中 `SetForegroundWindow` 在此值下仍可成功「还原」，它限制的是后台进程主动抢前台。
- 4.1.6 时代是否还有别的因素（例如 BepInEx 5 的 Doorstop 4.5.0 注入时机不同）未逐项排除。
